# V0 spike: Video Builder (ADR-0077) and the technical half of MG0 (ADR-0079)

Date: 2026-10-18 to 2026-10-19, the owner's MacBook Pro (Apple M5 Pro, 18 cores, 64 GB, macOS 27.0.1). Node.js 22.23.1 and
FFmpeg 8.1.1 were already installed. Everything else was downloaded with the owner's yes into a scratch folder outside
the repo (`~/Projects/wasifyai-spikes/v0/`): **hyperframes 0.8.171** (npm; repository HEAD `dc0e80e` on 2026-10-18,
Apache-2.0), **Chrome headless shell 152.0.7977.30** and **full Chrome for Testing 152.0.7977.30** (mac-arm64),
`playwright-core` 1.64.1 (library only, no browser), `gsap` 3.15.0 (npm; "Standard no charge" licence, owner cleared it for the
free desktop). No product code, ADR or plan was touched. Scripts and raw logs are in the scratch folder, not in the repo.

**How to read the numbers.** Four spikes shared the Mac. Load average was 3.8 to 7.5 during the renders (the other spikes
were running; a lock stopped two heavy runs overlapping, it could not stop other work). Times are therefore pessimistic and
noisy. Memory is the summed resident size (RSS) of the whole process tree sampled every 0.25 s, which counts shared pages
more than once: read it as an upper bound on what the process tree holds, not as the Mac's memory pressure. One machine,
one macOS: nothing here says anything about another Mac or another OS.

## Answer in one paragraph

HyperFrames renders on this Mac at about real time (a 60-second composition in 41 to 58 s, 2 to 3 GB), and the **same
input gave a byte-identical MP4 every time we compared** (two renders, 1 versus 4 workers, the pinned headless shell versus the installed Chrome 155, with
and without network). **A stock HyperFrames render is not sandboxed**: it starts Chrome with `--no-sandbox`, popup
blocking off, and no network limit, and a hostile composition rendered through the real CLI reached a service on localhost
and a remote host. A locked-down browser configuration that we built **does** stop every hostile case except memory
exhaustion, which only a fast watchdog limits (details and the exact flags below). The decision for V1 is therefore not
"can it be sandboxed" but **where the sandbox is applied**, because our harness is not HyperFrames' own launch path.
Transparent video works through HyperFrames itself (WebM VP9 with alpha and ProRes 4444, alpha verified by decoding a
frame). The system WebKit (WKWebView) rendered a seekable GSAP composition frame by frame with identical pixels
on three runs, so the Chrome component is not strictly required on a Mac; that was verified for GSAP and CSS only. Exact-text readback works on the DOM at the hold frame, but
**needs a pixel check next to it**, because the DOM still holds the text on frames that are visually empty.

## 1. HyperFrames: what it is and how fast it renders

Read first: the repository tree, the README, the `hyperframes-cli` and `hyperframes-core` skills, `doctor-browser.md`,
`preview-render.md`, and the browser manager and launch code in the published package. A composition is one HTML file: root
`data-composition-id`, `data-width`, `data-height`, `data-duration`; clips with `class="clip"` and `data-start`,
`data-duration`, `data-track-index`; one paused GSAP timeline registered as `window.__timelines["<id>"]`. CLI: `init`, `lint`,
`check` (lint, then one browser session auditing runtime errors, layout, contrast), `snapshot`, `preview`, `render`, plus
`doctor`, `browser`, `catalog`, `add`, cloud and Lambda variants. 21 skills ship in the repository. `render --format` takes
`mp4, webm, mov, gif, png-sequence, hls`; `--quality` `draft, looks (default), delivery`.

**Test compositions** (generated by one script, parametrised by size): *simple* = a 10-second animated title on a gradient.
*Heavy* = 60 seconds, six scenes: word-staggered title, four bullets, a 12-bar SVG chart with counting values, a 1600x900
picture with a slow zoom, a drawn line chart with a counting number, closing text; plus an animated full-frame
gradient and a progress bar the whole time. 720p30 (1280x720) and 1080p30 (1920x1080), H.264 MP4, default quality `looks`,
4 workers chosen automatically, GSAP vendored locally, fonts from the system.

| Simple 10 s, 1080p30 | 8.0 s, 8.8 s | 1.85 GB, 1.85 GB | 525 KB | capture 4.0, encode 1.1 |

Every run used the "screenshot capture" path with "hardware gpu" in HyperFrames' own summary line. **Not explained:** the
"setup" stage took 8.5 s once and 24 to 27 s on other heavy runs with the same input; I did not isolate it (load from the
other spikes is the likely cause, not verified). The 60-second heavy composition rendered faster than real time at 720p (1.2x to 1.5x) and about real time at 1080p (1.0x) under this load; more workers help
(1 worker took 2.1x to 2.5x as long as 4 for the 720p case). **Peak memory per render is 2 to 3 GB**, so a render fits beside a
resident local model on this 64 GB Mac; whether it does on a 16 or 32 GB Mac while a model is loaded was **not measured** (open
question 1 of ADR-0077 stays open for small Macs).

**Determinism.** SHA-256 of the MP4: identical for both runs of all four compositions; identical between 1 and 4 workers
(heavy 720p); identical between the pinned headless shell 152 and the installed Chrome 155 (simple and heavy, 720p); identical
with network denied at OS level (below); different for `--quality draft` (expected). The WebM (alpha) files differ by 16 bytes in the
container but all decoded frames are identical (hashes of 120 decoded RGBA frames match). **Not tested:** a second machine, another
macOS version, `--docker` (Docker was installed but not running), audio or video inputs, 4K. "Same machine, same pinned
Chrome" is what is proven.

**Things a product wrapper must handle** (found by reading and running):

- `init` checks "AI skills" against GitHub unless `HYPERFRAMES_SKIP_SKILLS=1`. Telemetry is on unless
  `HYPERFRAMES_NO_TELEMETRY=1` (or `DO_NOT_TRACK=1`); `telemetry status` confirmed "disabled" with it. `doctor` asks npm whether the version is
  the latest. The CLI writes `~/.hyperframes/` (config, history, caches) and `~/.cache/hyperframes/`, outside any
  per-app folder; those files already existed on this Mac from earlier HyperFrames use and my runs updated them. A managed component needs these set
  and the home folder redirected (the redirect was **not tested**).
- The stock `init` template loads GSAP from `cdn.jsdelivr.net`, and **the compiler downloads CDN scripts itself in Node**
  ("Failed to download CDN script"), outside the browser. With the network denied the stock template's render is
  blocked with `sub_timeline_script_failure`; a composition with GSAP vendored into the project rendered byte-identically with and
  without network. So **vendored libraries and fonts are a hard requirement**, and the lint step must reject any
  non-local URL before the compiler sees it. `lint` itself accepted my hostile composition (0 errors): it does not look for network use.
- `--browser-timeout` default 60 s, `HYPERFRAMES_BROWSER_PATH` and `PRODUCER_HEADLESS_SHELL_PATH` select the browser (both worked).
- The `hyperframes` npm package is 21.8 MB unpacked; `npm install` of it plus `playwright-core` and `gsap` took 6 s and
  134 MB of `node_modules` (78 packages added). `@hyperframes/producer` 0.8.171 is a separate npm package (puppeteer, hono, linkedom, ...); I did not
  read it for a launch hook.

## 2. Sandbox (ADR-0077 decision 4)

**What HyperFrames launches today** (read from its `browserManager`): `--no-sandbox`, `--disable-setuid-sandbox`,
`--disable-popup-blocking`, `--disable-extensions`, `--no-zygote`, `--disable-features=...IsolateOrigins,site-per-process...`,
no network restriction. Its `check` path already serves the page in-process through request interception, but passes requests to
other origins through (`request.continue()`), so it blocks nothing.

**Method.** A harness (puppeteer-core 25, the driver HyperFrames uses; headless shell 152; a fresh temporary profile per run, deleted
afterwards; the DevTools channel is a pipe, so no debugging port exists for a page to call) loads one hostile page per attack
and records what actually happened from the **browser's network events**, not from what the page says (a first version trusted the
page's own `fetch` result and mislabelled CORS-blocked responses as "blocked"; fixed). Four configurations:

| Config | What it is |
|---|---|
| **naive** | HyperFrames-style launch: `--no-sandbox`, popup blocking off, page loaded from `file://`, nothing else |
| **netcut** | hardened flags plus the network cut (below), page from `file://`, no interception |
| **intercept** | hardened flags plus the virtual origin with request interception, network not cut |
| **full** | hardened flags + network cut + virtual origin with interception + download deny + popup closing + watchdog |

**The exact configuration that worked** (config *full*):

```
launch: executablePath = pinned chrome-headless-shell, headless: 'shell', pipe: true, fresh userDataDir,
        ignoreDefaultArgs: ['--disable-popup-blocking', '--enable-automation']      # no --no-sandbox anywhere
flags:  --disable-extensions --disable-sync --disable-component-update --disable-background-networking
        --disable-default-apps --no-first-run --no-default-browser-check --disable-domain-reliability --no-pings
        --metrics-recording-only --mute-audio --deny-permission-prompts --disable-breakpad
        --disable-client-side-phishing-detection --safebrowsing-disable-auto-update
        --disable-features=Translate,MediaRouter,OptimizationHints,InterestFeedContentSuggestions
        --js-flags=--max-old-space-size=1024
        --proxy-server=socks5://127.0.0.1:9  --proxy-bypass-list=<-loopback>  --host-resolver-rules="MAP * ~NOTFOUND"
page:   CDP Browser.setDownloadBehavior {behavior:'deny'}
        the page is loaded from a virtual origin http://project.invalid/ ; page.setRequestInterception(true):
          answer a request from the project folder only (resolved path must stay inside it), `data:` and `blob:` pass,
          everything else is aborted (blockedbyclient)
        close any extra page target (window.open) immediately; dismiss alert/confirm/prompt
limits: heartbeat page.evaluate every 2.5 s; if it does not answer, CDP Runtime.terminateExecution, and if the page is
        still unresponsive kill the browser tree; wall-time limit per render; memory watchdog (below)
```

Why two layers: the **proxy and resolver rules** make the real network unreachable even if interception is bypassed (and
cover loopback, because of `<-loopback>`); the **virtual origin** removes `file://` from the picture entirely (Chrome refuses
`file:` loads from an http page) and serves only the project. Neither alone covers everything (rows below).

**Results.** Evidence is the browser's network events and the canary server's log.

| Attack | naive | netcut | intercept | full |
|---|---|---|---|---|
| Remote host, 6 request kinds (fetch, XHR, image, script, beacon; plus a WebSocket) to `example.com` | **left the machine**: beacon got HTTP 405; fetch, XHR, image, script were sent and only their responses were blocked by CORS / ORB (WebSocket inconclusive: example.com is not a WebSocket server) | all failed `ERR_PROXY_CONNECTION_FAILED` | all aborted `ERR_BLOCKED_BY_CLIENT` | all aborted |
| Read a canary file outside the project (script src, image, fetch, XHR, iframe) | **script and image READ it** (canary string read through `window.SECRET`; image loaded); fetch and XHR refused by Chrome, iframe unreadable | same as naive | all refused (Chrome blocks `file:` from an http origin) | all refused |
| Call a service on localhost (fetch, image, WebSocket, `localhost` name) | **reached: the canary server logged 4 hits** (fetch, img, WebSocket upgrade, name) | 0 hits (`ERR_PROXY_CONNECTION_FAILED`) | 0 hits (aborted; the WebSocket also did not arrive, cause not isolated) | 0 hits |
| Popup (`window.open` to a remote URL and to blank) | opened, stays open | opened (headless shell shows no popup blocker; closed by our handler in these configs) | opened, closed by handler | opened, closed by handler within the run; the popup page's own network was not separately measured |
| Download (blob link with `download`) | **file written** | none | none | none |
| Permission prompts (geolocation, camera, notifications) | denied / not granted | same | same | same |
| `alert()` | dialog shown; page blocks until handled (without a handler it hung and was killed after 3.1 s) | handled by our dismiss | handled | handled |
| `for(;;){}` infinite loop | hung until the harness killed it at 3.1 s: **nothing in this config stops it** | same | same | **stopped in 3 ms by `Runtime.terminateExecution`; the browser stayed usable** |
| Allocate 256 MB typed-array chunks without limit | 6.9 GB in under 0.9 s, emergency stop | 6.4 GB | 6.6 GB | 6.2 GB with a 200 ms watchdog (too slow, see below) |

Two further results:

- **`--js-flags=--max-old-space-size=1024` does not limit memory** for typed arrays and `ArrayBuffer`s (the attack reached 6 GB with the flag set). A
  memory limit has to be a **watchdog that samples the process tree's RSS and kills**. How fast it must be, same attack, limit
  set low, "full" config: 200 ms polling with a 2.5 GB limit let the tree reach **6.2 GB**; 50 ms polling / 2.5 GB limit stopped it at **3.4 GB**; 25 ms / 1 GB at **1.1 GB**;
  10 ms / 1 GB at 1.26 GB. The attack allocates several GB per second, so the limit must sit well below what the Mac can lose, with a 25 ms poll
  the overshoot was about 0.1 GB. macOS does not enforce `ulimit -v`; I did not test `RLIMIT_CPU` (the wall-time limit plus
  `terminateExecution` covered the loop).
- **An OS-level profile (`sandbox-exec`) stops the same attacks even under the naive flags.** `(deny network-outbound)` plus a `file-read*` deny on the secret folder:
  remote requests `ERR_ACCESS_DENIED`, file reads `ERR_FILE_NOT_FOUND`, canary 0 hits. More importantly it works on the
  **real HyperFrames render**: the stock render of a hostile composition (page text shows what each attack did) printed
  `LOCALHOST: reached`, `REMOTE example.com: reached`, `FILE: blocked` (the render serves the page from `http://localhost:<random port>`, so file reads
  fail by origin, not by sandbox), and the canary server saw 5 hits. Under `(deny network-outbound (remote ip "*:*"))` + `(allow ... (remote ip "localhost:*"))` the same
  render printed `REMOTE: blocked` and still `LOCALHOST: reached` (5 canary hits), and a normal composition rendered **byte-identically**
  to the unsandboxed render. `sandbox-exec` is deprecated by Apple but works on this macOS. **Closing the localhost gap at OS level was not solved**: a
  single-port deny rule I wrote blocked all loopback traffic (so the render could not reach its own server), and allowing only
  named ports needs fixed ports; HyperFrames' servers use random ones (a `PRODUCER_PORT` variable exists, not tried).

**What this means for V1.** The lock-down that works is a configuration of the browser launch and request handling, and the stock
CLI does not apply it. Two ways forward, not yet decided: (a) our engine adapter launches the pinned shell itself with
the configuration above and drives HyperFrames' libraries (`@hyperframes/producer`, `@hyperframes/engine`) or a patched path, with
"a hostile composition reaches nothing" as a CI test; (b) wrap the unmodified CLI in an OS profile (works for the remote
network, leaves localhost open, macOS only). (a) is the answer to ADR-0077 decision 4 as written; whether the library exposes the launch
hooks is unread and is the first question for V1. **Not tested:** WebRTC/STUN UDP, service workers, WebGPU/WebGL
reading, CPU-time limits beyond wall time, Windows and Linux, extensions of the page's own `Content-Security-Policy`.

## 3. Which browser

| | Chrome headless shell (CfT) | Full Chrome for Testing | The person's installed Chrome |
|---|---|---|---|
| Version used | 152.0.7977.30 (the build HyperFrames pins in its code; a 150.0.7871.124 build for macOS 12) | 152.0.7977.30 | 155.0.8059.84 |

| Memory in a render | 1.4 to 3.0 GB | n/a | 3.9 to 4.1 GB (36 processes), a `GoogleUpdater` process appeared |

- **Pinning.** `https://storage.googleapis.com/chrome-for-testing-public/<version>/mac-arm64/chrome-headless-shell-mac-arm64.zip`
  (and `chrome-mac-arm64.zip`) are plain versioned URLs; HyperFrames pins the version in code and installs through
  `@puppeteer/browsers` into `~/.cache/hyperframes/chrome`. SHA-256 of what I downloaded (our own pins; I did not find a
  checksum published by Google at these URLs): shell zip `1db16c16e72bedfa747ed01c207a3fe8ee7370c35f2094279eb8878c996e8c79`, full zip
  `441bef11445a8642333ad88b0a7ed31e6742ef7fbb212812ec2f371c4a1b38eb`. HyperFrames' docs say the pin exists because pixels drift between Chrome
  versions; on these two compositions 152 and 155 gave identical bytes, so the drift risk is real in general but was not
  observed on this content.
- **macOS signing and quarantine (measured).** Both Chrome for Testing binaries are **ad-hoc / linker-signed, no Team ID,
  not notarised** (`codesign`: `Signature=adhoc`; `spctl`: rejected; the `.app` also reports "code has no resources but signature indicates they must be present"). A file downloaded
  with `curl` carries only `com.apple.provenance`, no quarantine flag, and runs. When I put `com.apple.quarantine` on a **copy** of the shell binary, running it from a
  shell **produced no output for 8 s and had to be killed** (blocked pending Gatekeeper; whether a dialog appeared on screen I could not see; if the owner finds a stray
  security dialog it is from this test); after `xattr -d com.apple.quarantine` the same binary ran at once. So the app must download it
  **without** setting quarantine (an app that opts into `LSFileQuarantineEnabled` would set it; a Tauri / reqwest download is not expected to, **not verified with a Tauri app**) or clear the flag after verifying the hash.
- **Recommendation:** the pinned headless shell as the managed component; the installed Chrome as an opt-in with its version shown
  (it worked, but is larger in memory, may not exist, may be auto-updated under us, and starts Google's updater).

**Can WKWebView do it?** Experiment: a 117 KB Swift program (AppKit + WKWebView, an off-screen borderless window) loads the
composition from a file, and for each frame calls `timeline.seek(t)` then `takeSnapshot`, hashing the decoded pixels.

| Run | Frames | Result |
|---|---|---|
| Simple 10 s, 720p page, two runs | 300 | **all 300 frame hashes identical** between runs; 6.6 s, 45 fps |
| Heavy 60 s, 720p page, three runs | 1800 | **all 1800 hashes identical** across three runs; 41.6 s, 43 fps |
| Same frames against Chrome (SSIM, WebKit frame scaled to the 1280x720 MP4 frame) | 5 frames with text and charts | 0.91 to 0.97 (text hinting differs; the MP4 is also lossy); on gradient-only frames 0.99 |

So **yes for GSAP and CSS on this Mac: WebKit seeks deterministically and quickly.** It is a different engine, so output is **not**
pixel-identical to Chrome's, and it will differ again on Windows (WebView2) and Linux (WebKitGTK). Caveats: `requestAnimationFrame` never fires for a
window that is off-screen (I waited on a timer instead); snapshots come back at the display's pixel scale (2560x1440 for a 1280x720 page on this Retina screen); it needs a
window-server session (an app, not a daemon); the 1.0 GB figure counts only the host process, not WebKit's separate web-content and GPU processes. **Not
verified:** `<video>` and `<audio>` clips, web fonts, canvas and WebGL, HyperFrames' own runtime and lint (its
runtime talks to Chrome-specific hooks), encoding the frames. Conclusion: a native-WebKit renderer is feasible for a
GSAP-only subset on a Mac; it is a second engine to maintain, not a drop-in for HyperFrames. ADR-0077's idea of dropping the Chrome
download stays an option, not a result.

## 4. Transparent video

| Route | Command | Output | Alpha check by decoding a frame |
|---|---|---|---|
| **HyperFrames WebM** | `render --format webm` (composition with a transparent body) | VP9, `yuv420p`, tag `ALPHA_MODE=1`; 4 s 1080p lower third = 49 KB | hold frame: **93.7 % fully transparent**, panel pixel `(14,16,20)` with alpha **236** (= 0.92 x 255, as authored), corner `(0,0,0,0)`; first frame **100 % transparent** |
| **HyperFrames MOV** | `render --format mov` | ProRes 4444, `yuva444p12le`; 4 s 1080p = 9.9 MB | hold frame 93.7 % transparent, same panel alpha 236; first frame 100 % transparent |
| Playwright capture + FFmpeg (`render.mjs` from lower-thirds-skills, canvas template, MIT) | `node render.mjs page.html out.webm` / `out.mov` | WebM VP9 alpha 60.8 KB; ProRes 4444 `yuva444p12le` 22.8 MB (237 frames); its own alpha check passed (96 % see-through) | hold frame 96.4 % transparent in both files |
| HyperFrames WebM of an opaque composition | same | alpha 255 everywhere | as expected |

**Pitfall that would have hidden a failure:** FFmpeg's default VP9 decoder **drops the alpha** and returns an opaque frame; the decode check must use
`-c:v libvpx-vp9` (the lower-thirds script does this, and I used it). With the default decoder the same file read as 100 % opaque. The Playwright route launched
the installed Chrome (`channel: 'chrome'`); it needs only `playwright-core` and FFmpeg. **Conclusion:** HyperFrames writes both alpha formats itself, so
the Playwright route is not needed and nothing outside HyperFrames' sandbox is added. The ADR-0079 fallback is unnecessary for this part. Not tested: playback
in OBS, Premiere, Safari (HEVC alpha is a separate encode described in the pack's `delivery.md`), or ProRes in Final Cut.

## 5. Motion graphics: two skills adapted, and the exact-text readback

**Source read.** `iart-ai/lower-thirds-skills` at commit `aa8ef7ed9fa59d0a79fc57701e493cfd8197b5d8` and
`iart-ai/kinetic-typography-skills` at `fccc94bd325d824235ee9e715e65abde57b6513a`, both MIT, Copyright (c) 2026 iart.ai. Fetched
as files through the GitHub API only (no `git clone`, nothing installed, nothing run from them except `render.mjs`, which I read line by line first);
GIFs skipped. Read in full: both `SKILL.md`, `references/` (reveal recipes, delivery), `scripts/` (three shell
scripts, `render.mjs`), the lower-third template, both plugin manifests. Read by search, not line by line: the three example pages and the README text (grepped for URLs and install commands).
Copies and the MIT notice are in the scratch folder (`skills/`, `mg/NOTICE.md`).

**What fetches or installs (every one dropped or replaced in the adaptation):**

- Both READMEs: `npx skills add iart-ai/<pack>` and `/plugin marketplace add` (the install path ADR-0079 forbids), a list of 13 other `npx skills add` packs, and iart.ai links with tracking parameters. The kinetic `SKILL.md` ends with a link to iart.ai (also with tracking).
- Kinetic `scripts/seek-shot.sh`: `npx -y playwright screenshot` (fetches Playwright and, per its own comment, Chromium on first run). `SKILL.md` verify step: `npx playwright screenshot`. Its output contract asks for "one inline GSAP script from CDN".
- Kinetic references: `import ... from "gsap"`, `framer-motion`, `remotion` snippets (Remotion is excluded by ADR-0077); SplitText described as "free in GSAP 3.13+" (not checked, not used).
- Lower-thirds template: one `<link>` to `fonts.googleapis.com` per font family, and the `SKILL.md` tells the agent to add one per family (a run-time fetch). The three examples do the same. `README`/`SKILL.md` mention `npm i playwright-core` and `npx playwright install chromium`.
- `render.mjs` itself: **no network access, no install, no `eval` of remote code**; it spawns `ffmpeg` and `ffprobe`, writes to the working folder and the temp folder, and launches the installed Chrome (or Playwright's own Chromium if present).

**Adaptation** (`mg/gen.mjs`, a template filled with slot text, written for HyperFrames: root with `data-*`, one paused GSAP timeline,
GSAP vendored, system fonts, no CDN):

1. *Lower third* (from lower-thirds-skills): panel + accent bar + role tab built from DOM and CSS `clip-path`, animated by GSAP, transparent background, first and last frames empty,
   6 % title-safe margin, role set in capitals by CSS (the DOM keeps the user's spelling, the skill's rule). Rendered with `--format webm` and `--format mov` (section 4); 4 s at 1080p took 6.8 to 8.3 s, 2.2 GB.
2. *Kinetic title* (from kinetic-typography-skills): mask reveal per line plus per-character stagger (30 ms, 0.6 s, `expo.out`, as the skill specifies), full string kept in `aria-label` with fragments `aria-hidden`, split done in my own 10 lines (not SplitText). 5 s at 1080p took 6.8 to 7.4 s; MP4 112 KB, two renders byte-identical.

**What the skill's verify loop caught that the readback did not:** my first kinetic adaptation clipped the descender of the "g" in
"Designed" (the mask padding of 0.12 em was too small); I saw it only by zooming a frame. 0.28 em fixes it. The DOM readback and the pixel check below both passed on the clipped
version. A "look at it" step (the multimodal check of ADR-0079 decision 6, or a glyph-bounds test) is needed in addition to readback; that is not built or measured here.

**Exact-text readback.** A script loads the composition in the locked-down browser (config *full*, in the virtual origin), seeks
the same way the renderer does (`timeline.seek(t)`), and for every slot element reads (a) the drawn text from the DOM (concatenated text nodes, not the `aria-label`), (b) opacity, display and
how much of the text box is inside every `overflow` ancestor, and (c) a **pixel proof**: hide the element, screenshot its box before and after, and count pixels that change by more than 40/255 in any channel (at least 20 pixels). It compares
the NFC-normalised, whitespace-collapsed text with the slot input. Results (`DOM` = text equals input; `PROOF` = DOM and visible, opaque, inside its clip, and the pixels change when hidden):

| Case | At the hold frame | At the last frame |
|---|---|---|
| Lower third, correct text | DOM match, **PROOF true** (both slots) | DOM still holds the text, opacity 1, but **the pixels are empty (clip-path animated it away): PROOF false.** The last frame of a lower third is empty by design, so "read at the last frame" (ADR-0079 decision 7) works only for compositions that end on text; for the others read at the hold frame, or take the union over sampled frames |
| Kinetic title, correct text | DOM match, PROOF true | same (the title ends on the text) |
| A retyped name ("Maya Chan" for "Maya Chen"; "mption" for "motion") | **DOM mismatch detected**, both compositions | detected |
| Text in the same colour as its panel | DOM match, **pixel proof false** (this is why DOM-only is not enough) | n/a |
| A 54-character name in a 760 px panel | DOM match but only **42 % of the text box visible**: flagged (PROOF false) | flagged |
| Bengali ("মায়া চৌধুরী", "ডিজাইন প্রধান"), both templates | DOM match, PROOF true (ink painted). I did not check that the glyphs are correct (a missing-glyph box also paints ink) | same |
| `Tom & Jerry <Studio> "Q4"` and `</div><script>window.PWNED=1</script>` as slot text | DOM match; **the script did not execute** (HTML-escaped into text); the long strings overflowed the panel and were flagged | n/a |

The ADR-0079 idea holds with two changes: read at the **hold frame** (or over sampled frames), and pair the DOM read with the **pixel proof**. It does not detect clipped
descenders, a wrong font, or glyphs that render as boxes.

## Go or no-go

**V1: GO, with its first milestone changed.** The render engine, determinism, memory and speed are good enough for a Labs
feature, and the licence and browser questions have answers. But a stock HyperFrames render is not safe to run on model-written code. V1 must
start with **the sandboxed render path**, before any screen: our adapter owns the browser launch with the configuration in section 2 (or
patches the producer's launch), vendors GSAP and fonts and rejects non-local URLs at lint time (the compiler fetches CDN scripts in Node), runs the watchdog at 25 ms and
`terminateExecution`, and has the hostile-composition test (the attack pages in the scratch folder are the starting corpus) in CI. If the first question,
"can the producer's launch be replaced", is answered no, fall back to the OS-profile wrapper and accept that localhost stays open, or fork the launch code. A Mac-only
WebKit renderer is a possible later alternative, not a V1 dependency.

**MG1: GO for the template path** (slots filled verbatim, HyperFrames renders MP4, WebM alpha and ProRes alpha). Conditions: ship open fonts with the templates (system fonts differ per machine; the
lower-thirds check complained that Inter was not loaded when the Google link was removed), run readback at the hold frame with the pixel proof, add a look-check for clipped
glyphs. MG2 (model-written compositions) is **not assessed**: no model was evaluated in V0 (that is the other half of MG0).

## Not measured, and what the owner must decide

Not measured: another Mac or 16 and 32 GB memory with a model resident; `--docker`; Windows and Linux; audio and video inputs; 4K; HyperFrames Studio; the
model-quality half of MG0 (about 20 requests with and without a skill on three model tiers); WebRTC and service-worker escapes; CPU-time limits.

Owner decisions for V1: (1) which sandbox path, (a) our launch or (b) an OS-profile wrapper, after one short read of the producer's code; (2) accept that the managed
component must set `HYPERFRAMES_NO_TELEMETRY=1`, `HYPERFRAMES_SKIP_SKILLS=1` and redirect `~/.hyperframes`; (3) whether the installed Chrome is offered at all; (4) ship the open fonts (licences to
read before rule 12). Side effects of this spike outside the scratch folder: HyperFrames' own state in `~/.hyperframes` and `~/.cache/hyperframes` (updated by my runs); a copy
of the quarantine test lives only in the scratch folder.
